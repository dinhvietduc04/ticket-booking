# Seatly V2 and V3

This implementation covers all nine later features in `specs.MD`. The spec did not define a release split; V2 covers organizer operations and V3 covers venue design, admission, and pricing.

## Try it locally

1. Start PostgreSQL and Redis with `docker compose up -d postgres redis`.
2. Run `pnpm install` and `pnpm db:generate`.
3. Apply migrations: `pnpm --filter @ticket-booking/api exec prisma migrate deploy` with `DATABASE_URL` set. The existing `pnpm db:migrate` command also loads the root `.env`.
4. Start the API and web app with `pnpm dev:api` and `pnpm dev:web`.
5. Run `pnpm db:seed`, log in as `organizer@seatly.local` / `password123`, and visit `/organizer`. Seeding adds missing demo fixtures while preserving existing data and credentials. See the [demo scenario guide](demo-data.md) for all accounts and prepared workflows.

Use the organization selector to switch workspaces. New staff must first register an account; an owner or administrator can then add their email in Team. No invitation emails are sent.

## V2

| Feature            | Behavior                                                                                                                                                                                                                                                                                                                                                       |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Analytics          | Captured gross, refunds, net, average order, tickets, checkout conversion, refund rate, available inventory, and sales by UTC day, session, and ticket type. Date filters use order creation time. Currencies are reported separately.                                                                                                                         |
| Refund rules       | Default: 100% at 72+ hours, 50% at 24–72 hours, 0% inside 24 hours. Refund applies to the discounted total including service fees. All tickets in a customer-cancelled booking become unusable, including with a partial monetary refund. Used tickets cannot be customer-refunded.                                                                            |
| Event cancellation | Immediately stops sales and check-in, cancels pending checkout, blocks unsold inventory, and creates a durable refund task. BullMQ processes refunds with retries. Database recovery checks unfinished tasks every 30 seconds and on startup. Without Redis, recovery processes them directly. Prior partial refunds are topped up to the full captured total. |
| Audit UI           | Organization-scoped, paginated and action-filtered records of configuration, membership, promotion, layout, cancellation, and refund changes, written in the same transactions as those changes.                                                                                                                                                               |
| Promotions         | Organization-specific fixed or percentage discounts, maximum discount, date window, total uses, and per-customer limits. Apply once during checkout; the resulting booking total is immutable. Active unpaid checkout reserves a use; expiry/failure releases it. Captured/refunded orders continue consuming uses.                                            |
| Staff permissions  | Owners manage all roles; administrators manage staff/scanners and operational settings. Staff can view reports/events. Scanners only validate/check in tickets belonging to their organization. Global application admins have organization access. The final owner cannot be removed or demoted.                                                              |

Refunds use the existing **fake provider**. Refund records and payment counters are updated atomically and retries cannot refund twice. The interface does not transfer real money. Customer cancellation/refund notifications appear in booking history; external email delivery remains a separate integration.

Refund policy becomes locked once an event has pending or paid checkout, protecting existing purchases. Customer refunds are initiated from `/bookings/:id`. Organizer cancellation is under Events.

## V3

| Feature         | Behavior                                                                                                                                                                                                                                                                                                                                       |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Venue designer  | Create a hall in an existing venue, generate a seat grid, remove seats, set seat type, drag seats, or use arrow keys/numeric coordinates. Saving updates the physical seat layout used by the customer seat map. Scheduled halls permit position changes only.                                                                                 |
| Waiting room    | Per-session configurable admission capacity (0 disables), admission duration, stable FIFO positions, and opaque admission tokens. PostgreSQL serializes admission across instances. A token is bound to the customer and session and expires. New hold requests verify admission inside the reservation transaction.                           |
| Dynamic pricing | Per-session sold-percentage thresholds and base-price multipliers. The highest crossed threshold applies, with no compounding; blocked seats are excluded from capacity. Hold items snapshot price/currency. Changing rules or prices never changes existing held or purchased prices. Seat maps refresh prices periodically and on reconnect. |

Waiting users must log in. The queue advances on polling (every 10 seconds in the browser) and does not renew admission on each poll. Successful payment releases the admission used for that hold immediately, allowing the next waiting customer to enter on their next poll. Expired or completed customers rejoin at the end with a new token. A delayed or repeated payment cannot release a newer admission. Admission does not guarantee a seat. Existing holds can finish checkout after admission expires, up to the original hold expiry. Repeated reservation requests do not extend the five-minute hold window. A hold contains at most eight seats.

To test advancement, set capacity to 1 and admission duration to 60 minutes. Use two separate browser profiles logged in as different customers. A joins first and sees seats; B joins and sees position #1. Complete A's demo payment. Leave B's page open: within about 10 seconds it should show the seat map, with A's purchased seats unavailable. No refresh or timer expiry is needed. Start with a new hold after applying the admission-release migration; existing holds created before it have no admission snapshot and retain their original admission timeout.

The queue is a functional local/modular-monolith implementation, not a claim of having load-tested a 50,000-user launch. Load testing and a distributed edge waiting room remain deployment work.

## API additions

All organizer routes, refunds, notifications, and ticket scanning require a bearer token. Organization permissions are checked against the database for every request.

```text
GET    /api/organizer/organizations
GET    /api/organizer/organizations/:id
GET    /api/organizer/organizations/:id/analytics?from=ISO&to=ISO
GET    /api/organizer/organizations/:id/audit?page=1&action=EVENT_CANCELLED
POST   /api/organizer/organizations/:id/members
DELETE /api/organizer/organizations/:id/members/:memberId
POST   /api/organizer/organizations/:id/promotions
DELETE /api/organizer/organizations/:id/promotions/:promotionId
POST   /api/organizer/events/:id/refund-policy
POST   /api/organizer/events/:id/cancel
POST   /api/organizer/sessions/:id/settings
POST   /api/organizer/venues/:id/halls
POST   /api/organizer/halls/:id/layout
GET    /api/bookings/:id/refund-quote
POST   /api/bookings/:id/refund
GET    /api/account/notifications
GET    /api/sessions/:id/waiting-room
POST   /api/sessions/:id/waiting-room
```

`POST /api/bookings` accepts optional `promoCode`; `POST /api/sessions/:id/holds` accepts optional `admissionToken`. Hold reads and cancellation now verify ownership. Existing local demo identity fallback remains for customer MVP APIs; the new privileged operations never accept demo headers.

Schemas for new input bodies live in `packages/contracts/src/operations.ts`. New migrations preserve existing data and backfill historical hold prices from session seats. They cannot recover a historical price that was changed before this upgrade.

## Validation

```sh
pnpm typecheck
pnpm --filter @ticket-booking/api test
pnpm build
pnpm --filter @ticket-booking/web exec playwright install chromium
pnpm --filter @ticket-booking/web test:e2e
```

Database tests use isolated fixtures and clean up their own records. They cover pricing snapshots, promo contention/expiry, FIFO admission and token misuse, concurrent refunds, late webhooks, cancellation, used tickets, policy boundaries, roles, audit history, and layout constraints, alongside the existing 2-user/100-user contention tests. Browser tests exercise organizer configuration through the customer checkout/refund flow and a mobile layout check. Screenshots/traces are written under the ignored `apps/web/test-results` directory.
